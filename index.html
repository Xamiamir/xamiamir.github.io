CASE 01 · Email threat response

Strengthening Cyber Resilience through Phishing Email Investigation and Response in Healthcare Organizations

+
MXToolboxVirusTotalSplunkSpamAssassinPhishTool

Context

MediSure Health Network relies heavily on digital technology, which also makes it a target. One morning, staff received an email styled as a vendor invoice. It was a phishing attempt built to steal patient information and financial records. The systems were secure, but employees were the exposed point.

Purpose

Reduce immediate risk, improve future readiness, and stay compliant with HIPAA, while protecting MediSure’s reputation, operations and finances.

Investigation phases

  1. Review the suspicious emails.
  2. Validate domains and sender details.
  3. Analyse attachments and links for hidden threats.
  4. Examine network traffic with SIEM tools.
  5. Respond: block domains, reset accounts, isolate affected endpoints, update email filters.
  6. Monitor continuously for similar threats.
  7. Report and document everything.

Key objectives

  • Identify phishing indicators in headers, sender data and embedded links.
  • Validate sender authenticity with SPF, DKIM and DMARC checks.
  • Detect payloads and credential harvesting in links and attachments.
  • Correlate inbound and outbound traffic against known malicious IPs and domains.
  • Contain the threat and train staff to recognise similar attacks.

Outcome

Phishing attempts were identified and contained, the likelihood of future attacks dropped, staff awareness rose, and compliance improved. Employees became the first line of defence.

CASE 02 · SIEM and detection engineering

SIEM Implementation & SOC Detection Engineering on Thornbury Wealth Partners

+
SplunkSPLWindows EventCodesThreat intel lookups
3offices: London, New York, Toronto
2compromised accounts
142 MBclient data exfiltrated
7detection rules built

Objective

Detect and investigate a coordinated cyber attack against a UK-based financial services firm across three offices, using Splunk.

What I found

  • Brute force attacks that led to two compromised accounts.
  • Unauthorised privilege escalation.
  • 142 MB of client data sent to an external C2 server.
  • Backdoor accounts created for persistent access.
  • Ransomware deployed across multiple file servers.

What I built

SPL queries correlating failed logins, Windows EventCodes, outbound traffic anomalies and threat intelligence lookups. The result was 7 detection rules, scheduled alerts with severity classifications, and a SOC dashboard that brings every finding into one operational view.

CASE 04 · Malware Analysis

Malware Threat Intelligence & SOC Response — Grid Sentinel OT Security

+
FLARE-VM ProcMon RegShot Wireshark FakeNet-NG MITRE ATT&CK

Investigation Overview

Conducted a controlled malware investigation in a Windows 10 FLARE-VM laboratory, using a simulated critical-infrastructure security scenario. The objective was to investigate suspicious executable behaviour, identify indicators of compromise (IOCs), and develop evidence-based SOC response recommendations.

01 / Static Malware Analysis

  • Recorded the executable's SHA-256 identifier.
  • Used Dependency Walker to inspect imported DLLs.
  • Identified MSCOREE.DLL and _CorExeMain, suggesting a managed .NET executable.
  • Inspected the executable manifest with Resource Hacker.
  • Observed an asInvoker execution-level declaration.
  • Used Strings and PE inspection tools to support preliminary investigation.

02 / Dynamic Analysis Environment

  • Configured Windows 10 FLARE-VM in VirtualBox.
  • Created a VM snapshot before execution.
  • Configured host-only networking for the lab.
  • Recorded the VM address as 192.168.102.101.
  • Prepared ProcMon, Wireshark, RegShot and FakeNet-NG for behavioural monitoring.

03 / Network Investigation

FakeNet-NG recorded a DNS request associated with the suspicious executable for the domain:

fortyfive5.ydns.eu

The tool also logged an attempted TCP connection to the simulated destination 192.0.2.123 on port 5212. Wireshark captured repeated DNS queries and TCP SYN attempts.

These observations indicated attempted outbound communication consistent with possible command-and-control activity. Successful external communication or exfiltration was not confirmed.

04 / Process Behaviour Investigation

  • Used ProcMon Process Tree to investigate execution.
  • Observed multiple executable instances.
  • Reviewed associated processes including ermages.exe, cmd.exe and WerFault.exe.
  • Identified executable metadata referencing "License Review Application".
  • Documented process-spawning behaviour without assuming confirmed process injection.

05 / Registry Investigation

Compared pre-execution and post-execution registry snapshots using RegShot.

92 Registry keys added
21 Registry keys deleted

Registry differences were observed, but not every change could be attributed to the malware. Persistence through a Run key was not independently confirmed.

06 / Indicators of Compromise

  • Suspicious domain: fortyfive5.ydns.eu
  • Simulated destination: 192.0.2.123:5212
  • Suspicious process-spawning activity
  • Registry changes requiring further attribution

07 / SOC Response Recommendations

  • Investigate DNS requests for the identified domain.
  • Correlate network events with process execution logs.
  • Review endpoint persistence mechanisms.
  • Escalate suspicious execution to the incident response team.
  • Isolate affected endpoints when supported by incident evidence and response procedures.
  • Preserve process, registry and network evidence.

Investigation Outcome

Identified suspicious DNS activity, attempted TCP communication, process-spawning behaviour and registry modifications. Produced an evidence-led assessment distinguishing confirmed observations from suspected malicious capabilities.

CASE 05 · Threat intelligence

Strengthening Cyber Threat Intelligence and Malware Detection on NorthByte Cybersecurity

+
VirusTotalPythonYARAMITRE ATT&CKKali Linux

Objective

Take one suspicious file hash through the full threat intelligence lifecycle, from "is this file malicious?" to a report a stakeholder can act on.

What I did

  • Triaged the hash and reached a malware verdict with VirusTotal, using Python automation scripts.
  • Researched the sample and investigated the associated threat intelligence.
  • Wrote and tested a custom YARA detection rule.
  • Mapped the attack lifecycle to the MITRE ATT&CK framework.
  • Delivered a formal threat intelligence report covering IOCs, threat analysis, and detection and prevention recommendations. The stakeholder is not named for confidentiality reasons.

Takeaway

A single hash can unlock an entire threat picture if you know how to pull the thread. The work showed me why threat intelligence matters beyond alert triage: wider context, attack techniques and detection opportunities.
